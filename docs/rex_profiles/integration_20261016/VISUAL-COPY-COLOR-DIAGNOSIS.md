# Incompatibilidade preservada: cor do oráculo v1

O contrato b0f9f8d8 e o oráculo 8a0cd9d2 antecederam build e emulação. O v1 permanece imutável: RGB máximo 255, tolerância 7. Não foi aprovado. A corrida forward v1 tem 79/82 verificações aprovadas e 3 reprovadas, exclusivamente imagem absoluta original/repetição/cópia. A volta também 79/82, mesmas reprovações. A corrida final acrescenta verificações de identidade/oráculo/input e aprova 86/89, mantendo as mesmas três reprovações. Nenhum desses relatórios é PASS gráfico.

A previsão de RAM confere nos 484 bytes: origem, destino de 128, mapa de 224 bytes, quatro guardas de 16 e marcador. Original/repetição são idênticos. A diferença causal é exatamente os 162 bytes e 3309 pixels previstos. Core/canvas são idênticos. A volta produz a ROM original fbc72b25…0435. Essas evidências são necessárias mas não substituem a imagem absoluta reprovada.

As capturas têm canais de intensidade 0 ou 239; o oráculo pressupunha0 ou 255. A inferência inicial de que CRAM máximo implica saída255 foi minha e estava errada para este core. Não há evidência de erro no consumidor SGDK ou na conversão RGBA do aplicativo.

O core observado identifica `Genesis Plus GX v1.7.4 46a5521`; o hash binário pinado continua07c10476…8310b1. A revisão oficial correspondente é46a55214d0dab654e5a525ae0c54921ca9716872. Fonte oficial [vdp_render.c](https://github.com/libretro/Genesis-Plus-GX/blob/46a55214d0dab654e5a525ae0c54921ca9716872/core/vdp_render.c#L479) (SHA3627f311789c6cd774db903db716394e12148aa671d4b2001ab8c844077ac761) define modo normal como nível CRAM dobrado, no intervalo 0..14, e expande esse nível para RGB565. Para CRAM 7: nível 14 → R/B 29, G 59 → expansão do aplicativo 239/239/239. Essa derivação explica as capturas sem escolher constantes a partir delas. [libretro.c](https://github.com/libretro/Genesis-Plus-GX/blob/46a55214d0dab654e5a525ae0c54921ca9716872/libretro/libretro.c#L3487) (SHA4622426e697f692c89ff0d049f3bfcbc2a58e44fc2d393bbdd8302f65fc9b15c) negocia RGB565; frame_buffer.rs expande 5/6 bits por replicação de bits. A correspondência de revisão deriva do rótulo do binário, não de reconstrução bit a bit do core.

A instrução da missão é literal: “Não altere expectativas depois de observar o resultado.” Por isso não se ampliou tolerância, não se normalizou a captura, não se trocou core, não se corrigiu o esperado v1 e não se marcou a cena aprovada. Uma eventual referência v2 requer autorização explícita para essa exceção, contrato separado e novas corridas, preservando v1 reprovado. Pedido enviado durante o trabalho; a ausência de resposta não autoriza a mudança.
